# تكامل Manus API

## المبدأ والإصدار

استخدم **API v2** في أي تكامل جديد. اقرأ وثيقة endpoint المحلية المطابقة قبل كتابة جسم طلب أو افتراض حقل أو حد أو نطاق OAuth؛ هذه الملفات هي مصدر التفاصيل، بينما هذا الملف يوجّه القرار. شغّل `scripts/check_docs_freshness.py` قبل اعتماد تغيير يعتمد على API أو quota أو مصادقة، وتحقق من المصدر الرسمي عند وجود فرق.

لا تضع API key أو access token أو webhook secret في كود العميل أو سجل أو مثال ملتزم به. لا تنفّذ نشرًا أو حذفًا أو تأكيد إجراء خارجي من دون تأكيد المستخدم أو آلية عمل مفوضة وواضحة.

| الحاجة | المسار الصحيح | ابدأ بقراءة |

| رفع أو إدارة ملفات | دورة `file.upload` ثم endpoint المناسب | `file.upload.mdx` |

## المصادقة والأسرار

استخدم API key لتكامل أولي أو برنامج يعمل لصالح حسابه، واستخدم OAuth2 فقط عندما يبني تطبيق طرف ثالث تفويضًا نيابة عن المستخدم. لا تفترض أن OAuth يعمل مع كل endpoint؛ افحص وثيقة endpoint والنطاقات المطلوبة. خزّن الأسرار في مدير أسرار أو متغيرات بيئة خادمية، واكشف للعميل فقط ما يلزم لتدفقه.

إذا غاب نوع المصادقة أو النطاق أو التفويض، توقف واطلب الإعداد الصحيح. لا تستخدم قيمة وهمية في طلب حقيقي، ولا تفسر خطأ تفويض بوصفه عطلًا في منطق المهمة قبل التحقق من الرؤوس والنطاقات.

## دورة المهمة

1. أنشئ مهمة مستقلة أو تابع مهمة محفوظة بحسب جدول القرار، واحتفظ بـ `task_id` خارج نص المحادثة.
2. استخدم polling في نموذج أولي أو مسار محدود، واستخدم webhook في تدفق إنتاجي يحتاج إلى إشعار. اجعل معالجة webhook سريعة وقابلة للتكرار وتتحمل إعادة التسليم.
3. افحص أحداث الحالة، لا مجرد وجود استجابة HTTP. عند `waiting`، استخدم `task.sendMessage` إذا كان الطلب سؤالًا عاديًا للمستخدم؛ واستخدم `task.confirmAction` للحالات الأخرى فقط بعد تحقق من نوع الحدث و`confirm_input_schema` وتوافر التأكيد المناسب.
4. لا تتجاوز انتظار التأكيد، ولا تدفع `accept: true` تلقائيًا لتشغيل أثر خارجي أو ربط متصفح أو استخدام أسرار أو نشر.
5. سجّل request ID وحالة منقحة وسبب الخطأ. أعد المحاولة فقط عندما تكون العملية idempotent أو تحمل مفتاح تكرار ملائمًا.

## المخرجات المنظمة

استخدم Structured Output عندما يحتاج المستهلك إلى JSON، لا عندما تكفي إجابة بشرية. أرسل مخططًا جذره `object`، واضبط `additionalProperties: false` لكل object، وأدرج جميع الخصائص في `required` واستخدم nullable للحقول الاختيارية. لا تتجاوز عمق التعشيش المدعوم أو تفترض دعم كلمات JSON Schema غير موثقة.

المخطط يعمل مرة لكل انتهاء للمهمة؛ أعد تسليحه في رسالة لاحقة إذا احتجت استخراجًا جديدًا. افحص `success` قبل استعمال `value`: قد تكون `value` الافتراضية متوافقة بنيويًا حتى عندما يفشل الاستخراج. راجع `references/structured-output-checklist.md` قبل اعتماد المخطط.

## الويب هوكس والتشغيل

اجعل endpoint يقبل POST JSON عبر HTTPS، ويستجيب بسرعة، ويتحقق من التوقيع حسب وثيقة الأمان. افصل استقبال الحدث عن العمل البطيء عبر طابور أو آلية خلفية. احفظ معرف الحدث أو المفتاح المناسب لمنع التنفيذ المكرر، وسجل النتيجة بعد تنقيح البيانات الحساسة.

إذا لم يصل webhook، افحص قابلية الوصول وTLS ورمز الاستجابة ووقت المعالجة والتوقيع قبل تغيير التطبيق. لا تختبر باستخدام بيانات إنتاج حساسة أو callback عام غير محمي.

## الوثائق والحداثة

استخدم `docs/v2/index.json` للوصول إلى فهرس endpoint وبصماته، وشغّل الأدوات التالية:

```bash
python scripts/build_docs_index.py
python scripts/check_docs_freshness.py
```

اقرأ ملف endpoint المحدد عند تفاصيل الطلبات أو الاستجابات أو الحدود أو الأخطاء. لا تكرر في `SKILL.md` أرقامًا متغيرة أو أمثلة سرية؛ حدّث الفهرس وسجل الفرق عندما تتغير الوثائق.
