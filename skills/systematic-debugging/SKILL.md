# التشخيص المنهجي

## الهدف والحدود

حدّد **السبب الجذري القابل للإثبات** قبل تغيير الشفرة أو الإعدادات. عالج العَرَض بسرعة فقط إذا طلب المستخدم تخفيف أثر طارئ بوضوح، وافصل التخفيف المؤقت عن الإصلاح الدائم وسجّل مخاطره.

لا تجمع أو تطبع أسرارًا أو رموز دخول أو ملفات `.env` أو حمولة شخصية كاملة. لا تنفذ اختبارًا مدمّرًا على الإنتاج، ولا تغيّر عدة متغيرات في محاولة واحدة، ولا تدّعِ سببًا لا تدعمه أدلة قابلة للمراجعة.

## معلومات البدء

اطلب أقل قدر من البيانات اللازمة إن لم تكن متاحة: السلوك المتوقع، السلوك الفعلي، خطوات إعادة الإنتاج، النطاق الزمني، البيئة المتأثرة، سجل الخطأ بعد التنقيح، وما تغيّر مؤخرًا. راجع `references/redacted-evidence.md` قبل طلب السجلات أو نسخها.

إذا لم يكن العطل قابلاً لإعادة الإنتاج، فلا تقترح إصلاحًا. صمّم بدلًا من ذلك مراقبة أو تسجيلًا منقحًا أو اختبارًا يلتقط الواقعة التالية بأمان.

## سير العمل

### 1. تثبيت الأثر وحدود الحادث

صِف العطل في جملة قابلة للاختبار: «عند **المدخل/الحدث**، في **البيئة**، ينتج **سلوك فعلي** بدل **السلوك المتوقع**». ميّز بين أثر المستخدم، وشدة الحادث، وما إذا كان التخفيف الفوري مطلوبًا. حدّد نقطة التوقف إذا كان استمرار التشخيص قد يزيد الأثر أو يلامس بيانات حساسة.

### 2. إنتاج دليل قابل لإعادة التشغيل

أعد إنتاج المشكلة بأصغر حالة ممكنة. دوّن الأمر أو الخطوات، نسخة البرنامج، الإعدادات غير السرية ذات الصلة، والطابع الزمني. اقرأ رسالة الخطأ كاملة، بما فيها نوع الخطأ ومسار الملف والـ stack trace المنقح؛ لا تفسّر رسالة مقتطعة بوصفها سببًا جذريًا.

عند وجود طبقات أو خدمات متعددة، عيّن نقاط الانتقال بين العميل والخادم وقاعدة البيانات والمهام الخلفية أو الخدمات الخارجية. اجمع دليلًا منقحًا يوضح **أين** تتغير الحالة أو تفشل، ولا تسجل المدخلات الحساسة نفسها.

### 3. عزل الفرضية

قارن الحالة الفاشلة بحالة عاملة مماثلة، وافحص التغييرات الحديثة والاختلاف في الإصدار أو البيئة أو الإدخال أو الصلاحيات أو الترتيب الزمني. صغ فرضية واحدة بالصيغة: «السبب المرجح هو **X** لأن الدليل **Y** يفسر الفشل ولا يفسره البديل **Z**».

إذا تساوت فرضيتان أو غاب دليل فاصل، اختر تجربة صغيرة تميّزهما بدل تنفيذ إصلاحات متعددة. عند انكشاف اعتمادية خارجية أو حد منصة، راجع مرجعها الرسمي قبل تغيير الشفرة.

### 4. اختبار الفرضية بأقل تغيير قابل للعكس

أنشئ اختبارًا فاشلًا أو حالة إعادة إنتاج ثابتة إن أمكن. غيّر متغيرًا واحدًا فقط، واجعل التغيير قابلًا للعكس وسهل المراجعة. لا تخلط إصلاح الخطأ مع تحسينات تنسيقية أو إعادة هيكلة أو ترقية حزم غير لازمة.

إذا فشل الاختبار، ألغ التغيير أو وثّق نتيجة التجربة ثم ارجع إلى الأدلة. بعد محاولتين غير حاسمتين، أعد فحص نطاق المشكلة وفرضياتك. بعد ثلاث محاولات مدعومة لا تنجح، توقف واطلب من المستخدم قرارًا معماريًا أو وصولًا إلى الدليل الناقص بدل الاستمرار بالتخمين.

### 5. تطبيق الإصلاح والتحقق من الانحدار

طبّق أصغر إصلاح يعالج السبب الجذري، ثم تحقق من: حالة إعادة الإنتاج الأصلية، الاختبارات المجاورة أو رحلة المستخدم، حالة الفشل المتوقعة، وعدم تسرب بيانات حساسة إلى السجلات. اعرض بوضوح ما تغيّر، والدليل قبل/بعد، وأي مخاطرة متبقية، وخطوة الرجوع إن ظهرت آثار جانبية.

## مسارات قرار خاصة

| الحالة | الإجراء الصحيح |
|---|---|
| فشل بناء أو اختبار محلي | ثبّت نسخة الأداة والأمر الفاشل، ثم قارن المخرجات قبل تغيير المصدر. |
| خلل يظهر في الإنتاج فقط | اجمع مقاييس وسجلات منقحة ضمن نافذة زمنية محددة؛ لا تنسخ البيانات الشخصية ولا تجرّب تغييرًا مدمّرًا. |
| خطأ في تكامل خارجي | افحص request ID وحالة الاستجابة والحدود والوثائق الرسمية، مع تنقيح رموز التفويض. |
| تراجع أداء | قارن خط أساس وزمنًا أو استهلاكًا قابلًا للقياس؛ لا تنسب السبب إلى «بطء عام» بلا قياس. |
| تكرار إصلاحات فاشلة | أوقف التعديلات المتتابعة، وارفع مسألة تصميم أو اعتماد مفقود مع الأدلة التي جُمعت. |

## مخرج التشخيص

قدّم التقرير بهذا الترتيب: **وصف الأثر، إعادة الإنتاج، الأدلة، الفرضية المختبرة، التغيير أو سبب عدم تغييره، نتائج التحقق، خطة الرجوع أو الخطوة التالية**. اذكر بوضوح درجة الثقة؛ لا تحوّل ترجيحًا إلى حقيقة.
