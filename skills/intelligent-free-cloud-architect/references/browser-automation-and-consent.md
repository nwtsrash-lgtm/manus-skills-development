# أتمتة المتصفح والربط الآمن

## المبدأ

لا تعنِ عبارة «دون تدخل» أن يتجاوز النظام حسابات المستخدم أو يوافق على صلاحيات ودفعات نيابة عنه. المعنى الصحيح هو: **موافقة واحدة ومراجعة واضحة في bootstrap، ثم تشغيل مستقل قائم على webhooks وGit events وtimers بدلاً من المتصفح.**

## ما ينفذ تلقائياً بلا موافقة إضافية

| العملية | الشرط |
|---|---|
| قراءة مواقع عامة، خطط، وثائق، ومستودعات عامة | لا حساب أو تغيير حالة. |
| فحص متطلبات المستودع، إنشاء Docker/CI/backup files محلياً | لا push ولا تعديل حساب خارجي. |
| اختبار محلي، قياس البيانات، وإنشاء تقرير قرار | لا أسرار حية ولا حسابات خارجية. |
| متابعة حالة نشر أو workflow أو تنبيه تم تفويضه مسبقاً | اتصال موجود وصلاحية محدودة متفق عليها. |
| النشر التلقائي بعد كل push | workflow/secret/deploy target أُعدت ووافق عليها المستخدم مسبقاً. |

## ما يحتاج موافقة صريحة قبل التنفيذ

- تسجيل دخول أو إنشاء حساب أو قبول شروط خدمة.
- إدخال بطاقة، تغيير خطة، أو تشغيل خدمة قد تولّد كلفة.
- ربط GitHub OAuth أو تثبيت GitHub App أو منح وصول للمستودع.
- إضافة أو تدوير أو حذف secrets ومفاتيح SSH وAPI.
- إنشاء VM أو bucket أو database أو قواعد جدار ناري أو DNS أو عنوان عام.
- جعل مستودع خاصاً/عاماً، إلغاء أرشفته، أو push/merge/نشر production.
- تشغيل عملية تستدعي webhooks حقيقية إلى Salla أو Make أو أي نظام إنتاج.

اطلب موافقة موحّدة، محددة وقابلة للمراجعة. اذكر: الحساب/المزود، الصلاحية، الكائنات التي ستنشأ، ما إذا كانت بطاقة مطلوبة، العنوان العام المتوقع، وخطة الإلغاء.

## نمط bootstrap الآمن

1. جهز ملفات البنية وCI والنسخ محلياً وراجعها.
2. اعرض للمستخدم جدول «ما سينشأ وما سيُمنح».
3. بعد الموافقة، نفذ الربط مرة واحدة عبر المتصفح أو واجهة مزود الخدمة.
4. اختبر أقل مسار أولاً: commit اختبار → workflow → health check بلا بيانات إنتاج.
5. أضف secrets من لوحة آمنة، لا من ملف `.env` في Git ولا من دردشة.
6. شغّل restore test قبل السماح بـauto-deploy إلى الفرع الرئيسي.
7. وثق kill switch: تعطيل workflow، إيقاف service، وتعطيل مفتاح النشر.

## عدم استخدام المتصفح كعامل تشغيل

لا تستخدم جلسة متصفح لمراقبة خدمات كل دقيقة أو لتشغيل زر نشر يومياً. المتصفح وسيلة إعداد/مراجعة؛ أما التشغيل الدائم فيعتمد على:

- `push` أو `workflow_dispatch` أو release events من GitHub.
- webhooks موثقة وموقعة للتحفيز الخارجي.
- systemd timers أو cron للنسخ والمهام المحلية.
- health checks وheartbeats للمراقبة.

إذا لم يدعم النظام حدثاً موثقاً، لا تستبدله بصفحة متصفح آلية قبل تقييم API أو polling نظيف بمعدل متناسب ومشروع.

## قواعد السر والهوية

- خصص مفتاح SSH منفصلاً للنشر، محدوداً بمستخدم/أمر/مضيف واحد.
- خزّن known_hosts في secret منفصل، وفعل strict host key checking.
- استخدم GitHub Secrets للوصول وقت الـworkflow فقط؛ لا تطبع السر ولا تمرره كـcommand-line argument إن أمكن.
- استخدم OIDC بدل مفاتيح سحابية طويلة العمر حين تدعمه المنصة، بعد التحقق من الوثائق.
- امنح مفاتيح S3/R2/B2 صلاحية bucket وprefix المطلوبة فقط. افصل مفتاح النسخ عن صلاحية حذف الأرشيف.

## بوابة النجاح قبل الأتمتة الكاملة

لا تفعّل auto-deploy وtimers إلا عند تحقق ما يلي:

- workflow يعمل على SHA محدد ويعرض فشل الاختبارات بوضوح.
- restart لا يزيل data volume.
- health check يفشل عند النسخة السليمة المصطنعة ويتعافى عند النسخة الصحيحة.
- restore لنسخة SQLite حقيقية ينجح في بيئة منفصلة.
- يمكن تعطيل النشر أو إبطال المفتاح في أقل من دقيقة.
