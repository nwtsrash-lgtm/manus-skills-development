# أنماط معماريات هجينة

## النمط A: ملف SQLite محلي + استعادة مستقلة

**استخدمه عندما:** التطبيق قائم ويستخدم `sqlite3`، يوجد كاتب واحد، ويحتاج بيئة Python/Docker/متصفح لا تناسب serverless.

```text
Git private → بناء/نشر إصدار محدد → خادم واحد + volume دائم
                                      ├→ التطبيق يقرأ/يكتب SQLite محلياً
                                      ├→ مراقبة صحة
                                      └→ replication/backup → object storage مستقل
```

### قواعد التنفيذ

- اجعل `data/` أو مسار القاعدة volume منفصلاً عن image/release.
- فعّل WAL فقط بعد اختبار التطبيق، وراقب ملفات `-wal` و`-shm` ومساحة القرص.
- استخدم Litestream أو أداة واعية بـSQLite للنسخة شبه المستمرة؛ اضبط `sync-interval` وفق حد عمليات التخزين.
- خذ نسخة SQLite متسقة يومية، شفرها، وارفعها إلى مزود ثانٍ.
- استعد نسخة إلى مسار مؤقت وشغّل فحوص سلامة دورية.
- لا تشغّل أكثر من كاتب واحد أو mount مشترك بين عدة instances.

### متى لا تستخدمه

لا تستخدمه عند الحاجة إلى كتابات متزامنة عالية من عدة عقد، أو failover تلقائي بكتابة نشطة من موقعين، أو معاملات موزعة. انقل البيانات التشغيلية إلى قاعدة خادم مناسبة بعد تحليل الترحيل.

## النمط B: فصل حالة التشغيل عن البيانات التحليلية

**استخدمه عندما:** تريد استمرارية أفضل دون نقل قاعدة SQLite الكبيرة كلها.

| البيانات | المكان | المبرر |
|---|---|---|
| نتائج كثيفة وتحليل وكاش | SQLite محلي + نسخة كائنات | توافق وسرعة وعمليات قليلة. |
| مستخدمون وإعدادات وlocks وسجل آخر job | قاعدة مُدارة صغيرة | تبقى حالة النظام مرئية عند تعطل الخادم. |
| exports وملفات كبيرة ونسخ | object storage | فصل التخزين عن الحوسبة. |

لا تجعل القاعدة المدارة مرآة غير متزامنة للبيانات الحرجة من دون تعريف واضح للمصدر الحقيقي، واتجاه النسخ، وحل التعارض.

## النمط C: الوصول الخاص أولاً

**استخدمه عندما:** التطبيق لوحة داخلية أو يتعامل مع بيانات عملاء أو webhooks أو واجهة إدارية.

```text
المستخدمون المصرحون → شبكة وصول خاصة أو بوابة هوية → التطبيق
الإنترنت العام  ──X── لا يصل إلى منفذ التطبيق
```

ابدأ بشبكة خاصة أو بوابة هوية. أضف HTTPS ومصادقة ومحددات وصول عند تحويل التطبيق إلى عام. لا تعتمد على رابط غير معروف كطبقة أمن، ولا تعطّل آليات الحماية في التطبيق من دون طبقة بديلة موثقة.

## النمط D: إعادة بناء Serverless

**استخدمه عندما:** الواجهة وAPI عديمتا الحالة، الاستعلامات قصيرة، ولا توجد تبعيات نظام أو عمليات كثيفة أو كاتب SQLite محلي.

```text
واجهة ثابتة / Workers → قاعدة SQL managed → object storage
```

اعتبره مشروع ترحيل لا نقل استضافة. اكتب عقد API، طبقة repository، اختبارات تكافؤ بيانات، خطة إدخال تدريجي، وخطة rollback قبل الإغلاق النهائي للنظام القديم.

## نمط النسخ 3-2-1 المصغر

احتفظ بثلاث نسخ من البيانات على وسيطين، وإحداها في مزود مستقل:

1. نسخة العمل: volume المحلي.
2. نسخة قريبة: replication أو snapshot إلى object storage.
3. نسخة بعيدة مستقلة: أرشيف مشفر عند مزود آخر أو في موقع تملكه.

لا تخلط بين **replication** و**backup**. النسخ المتماثل قد يعكس حذفاً أو فساداً؛ لذا احتفظ بلقطات مؤرخة ذات retention.

## قائمة قبول ما قبل الإطلاق

| الاختبار | النجاح المطلوب |
|---|---|
| نشر من commit | التطبيق يعرض الإصدار الصحيح بعد فحص صحة. |
| restart | يبقى volume والقاعدة والuploads موجودة. |
| restore | استعادة إلى بيئة نظيفة وفحص مخطط القاعدة وعدد عينات من الصفوف. |
| سر مفقود | يفشل التطبيق بأمان ولا يسجل السر. |
| مفتاح تخزين | لا يصل إلا للـbucket/prefix الضروريين. |
| تعطل التخزين البعيد | التطبيق لا يفسد SQLite؛ يظهر تنبيه النسخ. |
| تعطل الخادم | يمكن إنشاء خادم جديد واستعادة البيانات ضمن RTO المتفق عليه. |
