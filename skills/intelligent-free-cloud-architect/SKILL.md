# مهندس السحابة المجانية الذكي

## الهدف

ابنِ توصية **صحيحة قابلة للتشغيل** لا قائمة مواقع. ركّز على استمرارية البيانات والأمان وقابلية الاستعادة قبل سهولة لوحة التحكم أو كلمة «مجاني».

اقرأ عند الحاجة:

- `references/decision-matrix.md` قبل التصنيف أو المفاضلة بين مزودين.
- `references/architecture-patterns.md` عند تصميم حل هجين أو عند وجود SQLite أو بيانات حساسة أو تشغيل دائم.
- `references/tozyw-oracle-runbook.md` عند العمل على مشروع **tozyw** أو Oracle Always Free أو النشر التلقائي من GitHub إلى خادم SQLite.
- `references/browser-automation-and-consent.md` عند طلب ربط خدمات أو تنفيذ إعدادات من المتصفح أو العمل التلقائي بلا تدخل يومي.
- `references/no-card-python-platforms.md` عند اشتراط تطبيق Python وقاعدة بيانات دائمة بلا بطاقة ائتمان؛ لا تستخدمه لإثبات ملاءمة مشروع يحتاج أكثر من 512MB أو عملية طويلة.
- `references/sqlite-backups-and-secrets.md` عند طلب نسخ SQLite إلى Google Drive أو GitHub، أو عند تصميم تشفير متغيرات البيئة على OCI/Render/GitHub.

استخدم القوالب فقط بعد مراجعة المسارات والأسرار وبيئة التشغيل:

- `templates/backup_to_rclone.py` لنسخ SQLite متسق إلى remote rclone مشفّر، مثل Google Drive.
- `templates/backup_to_github_release.sh` لنسخة ثانوية مشفرة بـage في GitHub Release لمستودع خاص منفصل.
- `templates/render-deploy.yml` لتشغيل الاختبارات ثم Render Deploy Hook بعد نجاح `main`.

## قواعد غير قابلة للتنازل

1. تحقّق من كل حد سعري أو تشغيلي من وثيقة رسمية حديثة للمزوّد. لا تعتمد على مقال مقارنة أو مقتطف نتائج بحث وحده.
2. صنّف العرض بدقة: **مجاني دائم ضمن حد**، أو **رصيد/تجربة مؤقتة**، أو **لوحة مجانية لكن البنية مدفوعة**، أو **برنامج ذاتي الاستضافة يحتاج خادماً**. لا تسمِّ الأخير «استضافة مجانية».
3. تحقّق صراحة من: الذاكرة وCPU، النوم/الإيقاف، القرص الدائم، حدود النقل، التخزين، قاعدة البيانات، النسخ الاحتياطي، المنطقة والسعة، البطاقة/الفوترة، وسياسة تجاوز الحدود.
4. ارفض أي خيار يخالف شرطاً صلباً حتى لو كان الأرخص. أمثلة الرفض: 512MB لتطبيق يتطلب أكثر، filesystem مؤقت لقاعدة SQLite، أو خدمة تنام بينما توجد مهام خلفية.
5. لا تفترض أن «يدعم SQLite» يعني أنه يشغل ملف SQLite. ميّز بين ملف SQLite محلي، ونسخ متماثل، وخدمة SQL متوافقة عبر API.
6. لا تنفّذ تسجيل حساب أو إضافة بطاقة أو تفعيل فاتورة أو منح صلاحيات أو نشر عام دون موافقة المستخدم الصريحة. بعد bootstrap الموافق عليه، اجعل النشر والنسخ والمراقبة آلية عبر أحداث Git أو timers أو webhooks، لا عبر تصرفات متصفح متكررة.
7. لا تنسخ أسراراً إلى Git أو سجلات أو مخرجات. استخدم متغيرات سرية، مفاتيح محدودة الصلاحية، ومصدراً واحداً للحقيقة لكل سر. عند النسخ إلى مزود لا تثق به بالكامل، شفّر الأرشيف على العميل قبل الرفع، واحفظ مادة فك التشفير خارج وجهة النسخ.

## سير العمل

### 1. صِف عبء العمل قبل البحث

استنتج من المشروع، أو اسأل فقط إذا غيّر الجواب الاختيار، عن:

| البند | ما يجب تقريره |
|---|---|
| وقت التشغيل | ثابت 24/7 أم HTTP متقطع أم مهمة مجدولة؟ |
| الموارد | CPU وRAM والقرص الحالي والمتوقع؛ افترض هامش نمو 50% على الأقل. |
| البيانات | SQLite/SQL، حجم البيانات، معدل الكتابة، عدد الكتّاب، حساسية البيانات. |
| الاعتمادات | Python/Node، Docker، متصفح للكشط، jobs، متطلبات نظام. |
| الوصول | خاص لفريق صغير أم عام، نطاق مملوك أم لا، وموقع المستخدمين. |
| الربط | GitHub، webhooks، APIs، S3، مصادقة، ووجهة النسخ الاحتياطي. |
| الاستمرارية | RPO مقبول لفقد البيانات وRTO مقبول للاستعادة. |

حوّل الغموض إلى افتراضات معلنة. لا تسأل عن تفاصيل تجميلية قبل تثبيت القيود الهندسية.

### 2. ابحث واختبر الحقائق

ابدأ بثلاث إلى خمس فئات مرشحة: حوسبة دائمة، serverless، PaaS، قاعدة بيانات مدارة، وتخزين كائنات/نسخ احتياطي. افتح وثائق التسعير والحدود والتخزين والـGit integration الرسمية لكل مرشح. استخدم مصادر ثانوية فقط لاكتشاف مرشحين أو مخاطر، ثم ثبّت الحكم بالمصدر الرسمي.

أنشئ **جدول الحقيقة** بالمقاييس التالية قبل الترشيح:

| المرشح | تصنيف المجاني | موارد التشغيل | النوم | ديمومة القرص | حدود البيانات/النقل | الفخ أو الشرط | الحكم |
|---|---|---|---|---|---|---|---|

ضع تاريخ التحقق وروابط مباشرة. إن تغيرت وثائق رسمية أو كانت غامضة، اذكر عدم اليقين ولا تملأ الفراغ بتخمين.

### 3. اتخذ القرار بحواجز ثم نقاط

طبّق أولاً حواجز الإقصاء: توافق runtime، الذاكرة، القرص الدائم، تشغيل الخلفية، عدد الكتّاب، المنطقة، والخصوصية. لا تمنح أي نقاط لخيار أخفق في حاجز.

بعد الإقصاء، قارن الباقي على: **استمرارية البيانات 35%، ملاءمة الموارد 20%، الأمان 15%، سهولة التشغيل 15%، اتصال Git والنشر 10%، هامش النمو 5%**. عدّل الأوزان فقط إذا غيّر المستخدم الأولوية صراحة.

لا تقدّم فائزاً واحداً بلا بديل. قدّم دائماً خيارين قابلين للحياة، أحدهما أخف تعقيداً، في جدول: المقاربة، المقايضة، الكلفة ضمن الحدود، وتعقيد الإعداد.

### 4. صمّم الربط كمنظومة لا كسلسلة مواقع

حدّد لكل مكوّن دوراً واحداً: الكود، runtime، قاعدة البيانات، التخزين، المصادقة، النسخ الاحتياطي، المراقبة. ارسم تدفق البيانات وحدد المصدر الحقيقي لكل نوع بيانات.

اتبع هذه القواعد:

- اجعل GitHub مصدراً للكود فقط، لا للبيانات الحية أو الأسرار.
- اجعل النشر idempotent: بناء إصدار محدد، فحص صحة، ثم تبديل آمن أو restart مضبوط.
- افصل مسار البيانات عن release: اركب volume دائم ولا تستبدله عند كل deploy.
- أعطِ مفاتيح التخزين صلاحيات bucket/prefix محددة؛ افصل مفتاح النسخ من مفتاح الاستعادة/الحذف متى أمكن.
- استخدم webhook موثق أو Git provider integration للنشر؛ لا تقترح polling إلا عند غياب webhook ووجود حاجة حقيقية.
- اختر نقطة وصول خاصة افتراضياً للوحة التشغيلية. عند النشر العام، أضف مصادقة وHTTPS وحدود وصول بدلاً من كشف المنفذ الداخلي.

### 5. حوّل الإعداد الأول إلى أتمتة مستقلة

ميّز دائماً بين **bootstrap** وبين التشغيل اللاحق. bootstrap هو الإعداد مرة واحدة، وقد يتطلب موافقة المستخدم على الحسابات والصلاحيات والأسرار. التشغيل اللاحق يجب أن يستمر بلا تدخل بشري:

| الحدث | المشغّل الصحيح | النتيجة |
|---|---|---|
| دمج/دفع commit إلى الفرع المحمي | GitHub Actions أو Git provider webhook | اختبار ثم deploy للإصدار نفسه فقط. |
| تغيير قاعدة SQLite | خدمة replication واعية بـWAL | نسخة متقاربة زمنياً إلى تخزين منفصل. |
| وقت يومي ثابت | systemd timer أو cron على خادم التطبيق | نسخة متسقة مشفرة واختبار محدود. |
| فشل النسخ أو health check | مراقبة/heartbeat موثقة | تنبيه قابل للمراجعة، لا إصلاح مدمر صامت. |

لا تستخدم المتصفح كعامل خلفي أو كبديل webhook. استخدم المتصفح فقط لإتمام bootstrap المصرح به أو للتحقق والمراقبة. لا تنشئ أتمتة تعدّل الإنتاج بلا gates: اختبارات، health check، قفل نشر، وrollback.

قبل ربط GitHub، تحقق أن المستودع قابل للكتابة وغير مؤرشف؛ المستودع المؤرشف read-only ولا يمكنه استقبال workflow أو commits جديدة. ضع مفاتيح النشر في GitHub Secrets أو استبدلها بـOIDC عند توفره. لا تمرر الأسرار في command lines أو ملفات workflow.

### 6. طبّق قواعد SQLite

إذا كان التطبيق يستخدم SQLite:

1. شغّل **كاتباً واحداً** لكل ملف قاعدة. لا تستخدم autoscaling أو عقدتين تكتبان في volume مشترك.
2. ثبّت ملف القاعدة وملفات WAL/SHM على قرص محلي دائم، لا على filesystem مؤقت أو network filesystem غير مختبر.
3. خذ نسخة متسقة بواسطة SQLite Backup API أو أداة واعية بـWAL؛ لا تنسخ `.db` عشوائياً أثناء الكتابة.
4. أضف replication إلى تخزين كائنات مستقل، مثل Litestream مع S3-compatible storage، إن كانت قيمة البيانات أعلى من قابلية استبدالها.
5. اختبر الاستعادة إلى ملف أو خادم جديد، ثم افحص الجداول والصفوف قبل الادعاء بوجود نسخ احتياطية.
6. انقل فقط حالة صغيرة إلى قاعدة مُدارة إن لزم تعدد العقد. لا تهاجر القاعدة الكبيرة إلى خدمة بعيدة قبل تصميم طبقة Repository واختبارات ترحيل وrollback.

### 7. صمّم النسخ الاحتياطي والتشفير

عند طلب نسخ SQLite، ابدأ من موقع ملف قاعدة البيانات الحي؛ لا من خدمة CI أو منصة نشر لا تملك volume. أنشئ لقطة متسقة عبر SQLite Backup API، ثم أرشفها وشفّرها قبل إرسالها إلى Google Drive أو GitHub. اقرأ `references/sqlite-backups-and-secrets.md` قبل اختيار الوجهة.

قارن خيارين على الأقل: Google Drive مشفر كنسخة خارجية أولى، وGitHub Releases مشفرة كنسخة ثانية محدودة، مع بيان حدود الحجم والاحتفاظ. لا تستخدم GitHub Actions artifacts أو filesystem مؤقتاً كنسخة وحيدة. شغّل النسخ من timer دائم بعد bootstrap الموافَق عليه، واختبر restore لا مجرد نجاح upload.

عند OCI Always Free، ضع أسرار runtime في OCI Vault وصمّم هوية instance أو وصولاً محدوداً لجلبها. ضع فقط أسرار CI الضرورية في GitHub Environment المحمي، وأسرار التطبيق فقط في منصة التشغيل. استخدم OIDC بدلاً من credentials طويلة العمر عندما تدعمه البنية وسياسة claims مقيدة؛ وإلا أنشئ مفتاحاً مستقلاً محدود الصلاحية وقابلاً للإبطال.

### 8. اختبر صحة المجاني والأمان

احسب الاستهلاك الشهري التقريبي للقرص والعمليات والنقل. اترك هامش 20%–30% عن الحد المجاني. إن كان التخزين يحاسب على العمليات، اضبط وتيرة المزامنة بدلاً من النسخ لكل تغيير صغير.

اذكر صراحة أي شرط بطاقة أو مناطق مدعومة أو شح سعة أو استرداد موارد خاملة أو تعليق مشروع غير نشط. لا تستخدم traffic اصطناعياً للالتفاف على سياسة الخمول؛ صمّم النسخ والمراقبة من احتياجات العمل الحقيقية.

### 9. أخرج توصية تنفيذية

اكتب ملخصاً حاسماً أولاً، ثم جدول مقارنة، ثم تصميم المعمارية وخطة من ست خطوات كحد أقصى. اشمل:

- ماذا يُستخدم الآن، وما لا يُستخدم ولماذا.
- مسار بيانات واضح من التطبيق إلى النسخ ثم الاستعادة.
- متغيرات سرية مطلوبة ومكان تخزينها، بلا قيم حقيقية.
- تعريف نجاح قابل للقياس: deploy من commit، بقاء البيانات بعد restart، وrestore ناجح، ووصول مصرح فقط.
- روابط ومراجع رسمية مرقمة لكل حقيقة زمنية أو تسعيرية.
- تمييز واضح بين خيار **بلا بطاقة** وخيار **مجاني ضمن حد لكنه يتطلب تحقق بطاقة**؛ لا تخلطهما.
- عند مشروع tozyw، الرجوع إلى `references/tozyw-oracle-runbook.md` وتطبيق تعريف النجاح فيه قبل ادعاء اكتمال الأتمتة.
- عند اشتراط عدم وجود بطاقة، الرجوع إلى `references/no-card-python-platforms.md` ثم إعادة فحص الحدود من المصادر الرسمية قبل الترشيح.
- عند طلب Google Drive أو GitHub للنسخ، الرجوع إلى `references/sqlite-backups-and-secrets.md` وبيان أن OAuth/مفاتيح التخزين تتطلب موافقة bootstrap منفصلة.

## أنماط رفض سريعة

| ادعاء شائع | التصحيح المطلوب |
|---|---|
| «مجاني» | هل هو دائم؟ هل يتطلب بطاقة؟ ماذا يحدث بعد تجاوز الحد؟ |
| «يوجد قرص» | هل هو persistent بعد sleep/redeploy؟ |
| «SQLite supported» | هل يمكن فتح الملف محلياً أم يجب API/refactor؟ |
| «GitHub connected» | هل المستودع قابل للكتابة وغير مؤرشف؟ وهل secrets مفصولة؟ |
| «نسخ احتياطي» | هل اختُبر restore فعلياً؟ وهل النسخة في مزود مستقل؟ |
| «موثوق للإنتاج» | هل توجد سياسة نوم/استرداد/عدم SLA أو حصة قد توقف الخدمة؟ |

## متى تصعّد

اطلب من المستخدم قراراً قبل أي إجراء مدفوع أو حساس. اقترح خبير أمن أو استشارة قانونية عند التعامل مع بيانات دفع أو طبية أو شخصية حساسة أو متطلبات امتثال ملزمة. اقترح خادماً مدفوعاً صغيراً عندما تكون الاستمرارية المهنية أو SLA شرطاً لا يمكن أن تضمنه الموارد المجانية.
