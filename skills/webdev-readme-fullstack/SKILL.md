# قالب WebDev Fullstack

## قرار الاستدعاء

استخدم هذا الدليل عندما يحتاج المنتج إلى حسابات مستخدمين أو قاعدة بيانات أو ملفات أو API خادمي أو منطق يحمي الأسرار. للتطبيقات الثابتة استخدم `webdev-readme-static`، وللتطبيقات المحمولة استخدم الدليل المحمول، وللتكامل المتخصص اقرأ مهارة التكامل ذات الصلة بعد هذا الدليل.

## سير العمل

1. افحص هيكل المشروع والملفات الأساسية قبل التعديل، وحدد ما إذا كانت الميزة تحتاج واجهة فقط أو إجراء tRPC أو مخطط قاعدة بيانات أو تخزينًا.
2. ابدأ بتعريف نموذج البيانات والصلاحية على الخادم، ثم أضف validation للإدخال وإجراء API محميًا عند الحاجة، وبعد ذلك ابنِ واجهة تستعمله بحالات تحميل وفشل واضحة.
3. ضع الأسرار وعمليات المزودين والكتابة إلى البيانات داخل الخادم. لا تثق بمعرف أو دور أو URL يرسله العميل وحده.
4. استخدم طبقات القالب بدل اختراع مسار موازٍ للمصادقة أو التخزين أو OAuth أو قاعدة البيانات. راجع المرجع المحدد قبل تعديل ملف أساسي.
5. اختبر المسار الناجح وفشل التحقق ومستخدمًا بلا تفويض، ثم راجع الواجهة على شاشة ضيقة وعريضة قبل الحفظ أو النشر.

## خريطة قرار سريعة

| الحاجة | البداية |
|---|---|
| صفحة أو مكون تفاعلي | بنية العميل وإرشادات الواجهة في المرجع. |
| قراءة أو كتابة بيانات | schema ثم query أو procedure مناسبة في المرجع. |
| حسابات وجلسات | مسار المصادقة الموجود؛ لا تبنِ callback أو cookie منافسين. |
| رفع ملف أو وسيط | مهارة `webdev-file-storage` ثم المراجع ذات الصلة. |
| نموذج أو خدمة AI | مهارة التكامل المناسبة، مع إبقاء الاستدعاء في الخادم. |
| نشر أو مشكلة قالب | قسم pitfalls والملفات الأساسية في المرجع. |

## السلامة والتحقق

لا تضع مفتاحًا أو connection string في العميل أو في مستودع Git. تحقق من الملكية في كل procedure يقرأ أو يغير سجلًا خاصًا، ولا تعتبر إخفاء زر تفويضًا. لا تعدّل مخططًا أو مسار مصادقة أو تخزينًا قبل قراءة مرجعه وتشغيل الاختبار الملائم. عند فشل تبعية أو migration، أوقف الأثر الجزئي وسجّل سببًا منقحًا بدل إعادة المحاولة العمياء.
